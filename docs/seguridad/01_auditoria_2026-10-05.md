# Auditoría de seguridad · 5 de octubre de 2026

Qué se probó, qué se encontró, qué se corrigió y qué sigue abierto. Las pruebas corrieron contra una copia local con **Oracle Free 23** (el mismo motor que producción) y con SQLite en las pruebas automáticas. Producción no se tocó.

## Herramientas

| Herramienta | Qué hace | Dónde |
|---|---|---|
| `backend/herramientas/auditoria_seguridad.py` | Recorre **todas** las rutas de la API (las lee de FastAPI) y les manda cargas de ataque en parámetros, ruta y cuerpo; revisa permisos con tres identidades (sin sesión, alumno, administrador), fuerza bruta, cuerpos gigantes y cabeceras. Devuelve un JSON con hallazgos por severidad. | Uso en su docstring |
| `backend/tests/test_seguridad.py` | Lo mismo en versión corta, en cada `pytest` (y en CI) | 9 pruebas |
| `backend/tests/test_proteccion_addon.py` | Integridad, marca de agua y política de copias del add-on | 4 pruebas |
| bandit, pip-audit, npm audit | Análisis estático de Python y dependencias con vulnerabilidades conocidas | A mano |

## Resultado

| Prueba | Resultado |
|---|---|
| Inyección SQL clásica (`' OR 1=1 --`, `UNION SELECT … FROM DUAL`, `'; DROP TABLE USUARIOS; --`) en cada parámetro y campo | Ninguna funcionó. Todo el acceso a datos pasa por SQLAlchemy con parámetros enlazados; no hay SQL armado con texto del usuario. |
| Inyección a ciegas por tiempo (`DBMS_PIPE.RECEIVE_MESSAGE`, `DBMS_SESSION.SLEEP`, `SLEEP`) | Ninguna respuesta se retrasó por la carga (la más lenta: 2.5 s, un inicio de sesión con PBKDF2). |
| Inicio de sesión con inyección | 401, sin entrar. |
| XSS (`<script>`, `onerror=`, `javascript:`) | La API responde JSON; nada se refleja como HTML. React escapa todo lo que muestra. |
| Recorrido de rutas (`../../etc/passwd` y variantes codificadas) | Ninguna ruta lee archivos fuera de lo suyo. |
| Permisos: alumno contra rutas de administración, alumno contra el progreso de otro, sin sesión contra rutas con sesión | 403 / 401 en todos los casos. |
| Fuerza bruta | La cuenta se bloquea 15 minutos a los 5 fallos (423) y la IP se frena con 429. |
| Cuerpos gigantes | 413 por encima de 2 MB (`AMATISTA_MAX_CUERPO`); Caddy corta en 1 MB. |
| **Total** | **1,449 peticiones, 69 rutas, 0 hallazgos** (después de los arreglos de abajo). |
| bandit | 0 altos. 2 medios, falsos positivos revisados: `red.py` (abre URLs, pero solo `http(s)://`) y `diagnostico_oracle.py` (nombres de tabla de una lista fija). |
| pip-audit / npm audit | Sin vulnerabilidades conocidas en las dependencias. |

## Corregido hoy

| Problema | Riesgo | Arreglo |
|---|---|---|
| Los errores de Oracle llegaban completos al navegador | Revelaban nombres de tablas, columnas y del esquema | Solo llega el código (`ORA-00942`) y un folio; el detalle queda en el log con ese folio (`api/comun.py`) |
| Sin cabeceras de seguridad cuando la API se expone sin Caddy (hoy, puerto 8000) | Sniffing de tipos, la API dentro de un iframe ajeno | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` desde la propia API (`main.py`) |
| Respuestas con datos personales sin `Cache-Control` | Un proxy o una computadora compartida podía guardarlas | `no-store` en sesión, progreso, administración y datos del add-on |
| `/docs` y `/openapi.json` públicos | Mapa completo de la API para un atacante | `AMATISTA_OCULTAR_DOCS=1` (Caddy ya los cerraba) |
| Sin límite de tamaño del cuerpo en la API | Agotar memoria con una petición enorme | 413 por encima de `AMATISTA_MAX_CUERPO` |
| Límites por IP con un aula detrás de una sola IP | El aula entera recibía 429 en el piloto | Límites por cuenta en rutas con sesión; registro e inicio 60/min por IP; la cuenta se sigue bloqueando a los 5 fallos |
| Add-on sin forma de saber si una copia fue alterada ni de quién salió | Copias modificadas o redistribuidas sin rastro | Integridad por archivo y marca de agua firmada (ver [protección del código](02_proteccion_del_codigo.md)) |

## Abierto, por prioridad

1. **La API de producción viaja en HTTP plano** (`http://158.101.118.222:8000`). Contraseñas y tokens cruzan Internet sin cifrar. Se cierra en la [fase 2 del plan de despliegue](../despliegue/2026-10-05_plan_de_despliegue.md#fase-2-https-con-el-dominio-9-y-10-de-octubre).
2. **El repositorio es público.** Cualquiera puede leer el código del servidor, el motor y el add-on. No hay secretos en el repositorio (revisado), pero conviene hacerlo privado después de mover la PWA a Cloudflare Pages ([fase 4](../despliegue/2026-10-05_plan_de_despliegue.md#fase-4-comprobar-contra-producción-y-cerrar)).
3. **Producción usa el usuario `ADMIN` de Oracle.** Si alguien comprometiera la API tendría todos los permisos de la base. El script 004 crea `AMATISTA_APP` con lo mínimo (T-004).
4. **`AMATISTA_SECRETO_FIRMA` no existe todavía en el servidor**: sin él, las descargas salen sin firma. Fase 1 del plan.
5. **Política de contenido (CSP) para la PWA**: pendiente de probar con todas las páginas.

## Repetir la auditoría

```bash
cd backend && source venv/bin/activate
python herramientas/auditoria_seguridad.py --url http://localhost:8000 \
  --token-admin <token de un admin de prueba> --token-alumno <token de un alumno de prueba> \
  --salida auditoria.json
```

Sale con código 1 si hay hallazgos altos o críticos. Contra producción, solo con cuentas de prueba: la herramienta provoca bloqueos de cuenta a propósito.
